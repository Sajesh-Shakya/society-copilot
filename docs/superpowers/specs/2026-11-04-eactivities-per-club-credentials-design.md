# Per-Club eActivities Credentials — Design

## Context

Plan 2 (routing/auth + the multi-tenancy scoping sweep) made every table and query in this app club-aware, but one integration was deliberately left out: eActivities. `lib/eactivities/client.ts` reads a single global `EACTIVITIES_API_KEY`/`EACTIVITIES_CSP_CODE` pair from env vars — Judo's own credentials, hardcoded at the environment level. A temporary `EACTIVITIES_CLUB_SLUG` env-var gate in `lib/attendance/actions.ts` refuses eActivities-dependent actions (`getEventSignups`, `createSessionFromSignup`) for any club other than the one named by that var, with a message pointing admins at CSV import instead.

A `club_credential` table already exists (`supabase/migrations/20261031090200_create_club_credential_table.sql`: `club_id, provider, credentials jsonb`, RLS force-enabled, primary key `(club_id, provider)`), created during Plan 1 in anticipation of exactly this work, but nothing reads or writes it yet.

eActivities itself is already scoped per-club by design: Imperial's eActivities API authenticates against a specific "centre" (CSP code) with its own API key — every Imperial Union-affiliated club/society has its own CSP code and key. The current env-var approach doesn't reflect a real limitation of the API; it's just the shortcut Plan 1 took to get Judo working. This plan removes that shortcut: credentials move into `club_credential`, `EactivitiesProvider` is constructed per-request from the requesting club's own credentials, and the `EACTIVITIES_CLUB_SLUG` gate is replaced by a real fact (does this club have a credential row?) instead of a hardcoded slug.

**Decided, not open:** Pluto is out of scope (no real API client exists for it today — `pluto_api` is just a literal source tag on purchase rows, not a live integration; `club_credential`'s `provider` constraint already allows `'pluto'` for whenever that changes, but this plan touches `eactivities` rows only). Credentials are stored as plaintext JSON in `club_credential.credentials` — no new encryption-at-rest layer, matching every other secret in this codebase (Resend key, cron secret, sync trigger secret are all plain env vars; this table already restricts access to the service-role client via forced RLS, the same protection level as everything else). Provisioning is a one-off script (`scripts/set-eactivities-credentials.ts`), matching the existing `scripts/create-admin.ts` convention — no admin UI.

## Design

**`lib/eactivities/credentials.ts` (new)** — `getEactivitiesCredentials(clubId: string): Promise<{ apiKey: string; cspCode: string }>`. Looks up `club_credential` where `club_id = clubId and provider = 'eactivities'`. Parses `credentials` as `{ apiKey: string; cspCode: string }`. Throws the existing `EactivitiesNotConfiguredError` (from `lib/eactivities/types.ts`) if no row exists, or if the row exists but is missing either field (a corrupt/partial row should fail loudly, not silently proceed with `undefined`).

**`lib/eactivities/client.ts`** — `eactivitiesFetch<T>(path: string, apiKey: string): Promise<T>` and `cspPath(path: string, cspCode: string): string` both drop their `process.env` reads and take the relevant credential as a parameter instead. Behavior (Basic auth with empty username, the no-retry policy on 401/403, the CSP-code path-prefixing) is otherwise unchanged.

**`lib/eactivities/provider.ts`** — `EactivitiesProvider`'s constructor takes `{ apiKey: string; cspCode: string }` and stores it; every method (`getEvents`, `getEvent`, `getSignup`) passes `this.credentials.apiKey`/`this.credentials.cspCode` into `eactivitiesFetch`/`cspPath` instead of those functions reading env vars themselves.

**`lib/attendance/actions.ts`** — the module-level `const provider = new EactivitiesProvider();` singleton is removed (it can no longer be constructed without credentials, and different calls may be for different clubs). `getEventSignups(clubSlug, eventId)` and `createSessionFromSignup(clubSlug, input)` both drop their `EACTIVITIES_CLUB_SLUG` env-var check; immediately after `requireAdmin(clubSlug)` resolves `clubId`, they call `getEactivitiesCredentials(clubId)` inside a try/catch, catching `EactivitiesNotConfiguredError` specifically and rethrowing `new Error("eActivities isn't available for this club yet — use CSV import instead.")` — the exact same message currently shown, so no user-facing copy changes. On success, they construct `new EactivitiesProvider(credentials)` and use it for that one call.

**`lib/attendance/sync.ts`** — `syncSessionAttendance(sessionId, clubId, options = {})`'s existing `const provider = options.provider ?? new EactivitiesProvider();` line becomes `const provider = options.provider ?? new EactivitiesProvider(await getEactivitiesCredentials(clubId));`. Test callers that pass `options.provider` (a fake) are unaffected — the credential lookup only runs for the real, non-test path. `createSessionFromSignup`'s existing best-effort `try { await syncSessionAttendance(...) } catch { /* swallow, non-fatal */ }` around the initial post-create sync continues to absorb a missing-credential error exactly like any other sync failure — no new handling needed there.

**The two HTTP sync routes** (`app/api/cron/eactivities-sync/route.ts`, `app/api/sessions/[sessionId]/sync/route.ts`) need no changes — both already resolve `session.club_id` before calling `syncSessionAttendance(sessionId, clubId)`, and credential resolution now happens inside that function.

**`scripts/set-eactivities-credentials.ts` (new)** — `node scripts/set-eactivities-credentials.ts <club-slug> <api-key> <csp-code>`. Resolves the club by slug (same pattern as `create-admin.ts`), upserts a `club_credential` row with `provider: 'eactivities'` and `credentials: { apiKey, cspCode }` (`onConflict: 'club_id,provider'`). Prints a confirmation with no secret echoed back (unlike `create-admin.ts`'s one-time password print, there's no reason to redisplay a key the caller already typed in).

**Migrating Judo:** once this ships, running `node scripts/set-eactivities-credentials.ts judo <EACTIVITIES_API_KEY value> <EACTIVITIES_CSP_CODE value>` (copying the two current env-var values) gives Judo a real `club_credential` row, after which `EACTIVITIES_API_KEY`, `EACTIVITIES_CSP_CODE`, and `EACTIVITIES_CLUB_SLUG` are all dead env vars — removable from Vercel as a follow-up ops step, not part of this plan's code changes (the code works correctly whether or not those vars still exist, since nothing reads them anymore after this plan).

## Testing

- `getEactivitiesCredentials`: a new integration test — a club with a seeded `club_credential` row returns the parsed `{ apiKey, cspCode }`; a club with no row throws `EactivitiesNotConfiguredError`; a row with a malformed `credentials` payload (missing `apiKey` or `cspCode`) also throws rather than returning a partial object.
- `client.ts`/`provider.ts`: no existing test coverage today (confirmed — `tests/unit/` and `tests/integration/` have no eActivities-specific spec files), so there's nothing to update; the signature change itself carries no behavior change (Basic auth header construction, CSP path prefixing, the no-retry 401/403 handling are all unchanged, just parameterized instead of reading env vars).
- `syncSessionAttendance`: existing tests already inject a fake `provider` via `options.provider`, so they're unaffected by this change — add one new test confirming that when NO fake provider is supplied and the target club has no `club_credential` row, the real credential-resolution path throws `EactivitiesNotConfiguredError` before any HTTP call is attempted.
- `getEventSignups`/`createSessionFromSignup` remain untestable directly (same `requireAdmin`-needs-a-real-request-context limitation as every other Server Action in this codebase) — covered only by the `getEactivitiesCredentials` unit coverage plus a manual check.

## Review Focus

- A club with no `club_credential` row must get the same clear "use CSV import instead" message it gets today — not a raw stack trace or a generic 500. Owned by the try/catch in `getEventSignups`/`createSessionFromSignup`.
- A `club_credential` row that exists but has a malformed `credentials` payload (e.g. missing `cspCode`) must fail loudly (throw) rather than silently making a request with `undefined` in the Basic-auth header or the URL path — owned by `getEactivitiesCredentials`'s explicit field checks.
- Judo's existing eActivities flow must keep working identically after its credentials move from env vars into `club_credential` — no behavior change for the one club that already uses this integration today, only a different credential source.
- The provisioning script must never echo the API key back after storing it (it was just typed into the terminal, no need to redisplay it) and must use `onConflict: 'club_id,provider'` so re-running it for the same club (e.g. to rotate a key) updates the existing row instead of erroring on the primary key.
